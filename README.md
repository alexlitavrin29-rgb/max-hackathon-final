# Точка опоры

Бот и miniapp в MAX для воспитанников и выпускников центров содействия семейному воспитанию. Помогает разобраться с работой, жильём, выплатами и документами, выбрать шаги и вернуться к своему плану.

Команда «ЗДОРОВЫЕ»: Александр Литаврин — продукт и разработка; Андрей Воронин — исследование потребностей; Павел Уткин — интерфейс и пользовательский опыт.

Код v4 сохраняет исправления навигации MAX и классификации финансового вопроса. Дополнительно проверка БД ограничена 2 секундами и возвращает 503 при недоступности, названия целей и дел отклоняют нулевой символ до сохранения, heartbeat бота записывается атомарно и переживает временную ошибку записи. Рабочий Compose регулярно проверяет HTTP админки; это статус Docker health, а не автоматический перезапуск нездорового процесса. В инструкции исправлен номер публикации на 11, в OpenAPI описан ответ health 503. Сводка проверок приведена в `VERIFICATION.md`.

Работающий продукт: https://max.ru/t143_hakaton_max_bot . Собственный API: https://135-106-229-210.sslip.io . Две версии презентации: [для жюри](presentations/Tochka_Opory_JURY.pdf) — служебная информация в начале и техническая реализация после команды; [для показа](presentations/Tochka_Opory_SHOW.pdf) — технические приложения после «Спасибо за внимание». Письмо о заинтересованности находится после блока пилота в обеих версиях. Рабочие ключи не включены в публичные файлы и передаются организаторам отдельно.

## Сценарий проверки и ожидаемый результат

В своём MAX: «Найти ответ» → вопрос о выплатах после выпуска → выбор конкретной меры при уточнении → ответ и источник → выбранные пользователем шаги → дата дела → «Планы» → выполнение → повторное открытие. Результат — сохранённый личный план с датой и отметкой. Сервис не назначает выплату и не подтверждает право через госреестр.

Дополнительно: маршруты жилья и работы с ручным статусом, вакансии и аренда с переходом к источнику, справочник, избранное, резюме. Наличие объявлений зависит от выдачи поставщика. Пустая выдача не означает отсутствие вариантов во всём источнике. Подробная демонстрация — `README.md`.

## Состав и архитектура

```text
MAX bot (один poller) ── общий движок/подготовленные материалы ── поставщики
MAX miniapp ── HTTPS/Caddy ── FastAPI ── PostgreSQL
                                │         ├─ планы, дела и статусы
                                │         ├─ сеансы и избранное
                                └─ LLM    └─ черновики и резюме
Редактор сценария ── отдельная авторизация ── опубликованная конфигурация
```

Стек: Python 3.12, FastAPI, asyncpg, PostgreSQL 16, HTML/CSS/JavaScript, MAX Bridge, HTTPX, Docker/Caddy. Версии библиотек — в requirements и package-lock. Redis/RabbitMQ этому Compose не нужны. Admin редактирует сценарий, для прохождения опубликованного пути не требуется и в локальном Compose не открыт; код редактора передан.

LLM разбирает запрос, подбирает подготовленный материал и предлагает шаги. Правовые факты и объявления берутся из отдельных данных/поставщиков. Пользователь подтверждает добавление дел. Фоновые уведомления выполняет бот; локальная сборка по умолчанию не отправляет сообщения.

## Запуск всех необходимых локальных компонентов

Для запуска нужны Docker Engine, Docker Compose v2 и доступ к Registry/PyPI при первой сборке. Для вспомогательных runner на компьютере нужен Python 3.11+, для браузерных проверок — Node.js/npm и браузеры Playwright. Скрипт `check_api.py` также использует библиотеки из `requirements-validation.txt`; внутри проверочного Docker-образа они уже установлены. Скопировать `submission/.env.example` в `submission/.env`, выбрать локальный пароль PostgreSQL и из этого каталога выполнить:

```sh
docker compose --env-file submission/.env -f submission/compose.yaml up -d --build
```

Открыть http://127.0.0.1:18876. Публикуется только loopback 18876; API внутри Docker — 8766, PostgreSQL — 5432 только во внутренней сети. Seed устанавливает сценарий в новую БД и явно применяет аддитивные миграции. Существующий сценарий не заменяется. Результаты свежей сборки и тестов — `VERIFICATION.md`.

Это ограниченный локальный preview: личные планы, справочник и статусы требуют подписанного MAX-сеанса. Полный путь проверяется в опубликованном MAX либо интеграционными тестами с синтетическими подписями на отдельной БД. Контейнеризация не заменяет доступность продукта в MAX.

| MINIAPP_BOT_NAME | Имя MAX-бота |
| PLANNER_ENABLED / PLANNER_AI_ENABLED | Включены в примере |

| PROXYAPI_API_KEY | Ключ внешнего LLM; нужен для новых модельных ответов |

| HOUSING_API_KEY | ReefAPI, аренда |

Рабочие ключи отсутствуют в исходниках, примерах и fixtures. Для воспроизведения внешних интеграций используются согласованные закрытые доступы или ключи проверяющего. Без них нельзя считать поставщика проверенным. Ошибки не заменяются выдуманными объявлениями.

Интеграции: MAX (вход, бот, Bridge), «Работа России» и HeadHunter (вакансии), ReefAPI (аренда), подготовленный каталог помощи, официальные/правовые ссылки в карточках, ProxyAPI (LLM). Прямой подачи заявлений и доступа к госреестрам нет. Доступность, тарифы и условия внешних сервисов определяют поставщики.

## Данные и воспроизводимые тесты

`submission/scenario.json` — конфигурация публикации production №11 без пользовательских таблиц. Локальный номер публикации создаётся заново и может отличаться. Включены каталоги и синтетические fixtures; исключены production-переписка, планы, резюме, токены сеансов и дампы. Включены файлы зависимостей и тестовые инструменты.

Структурные проверки после запуска:

```sh
docker compose --env-file submission/.env -f submission/compose.yaml exec -T miniapp python -m openapi_spec_validator openapi.yaml
docker compose --env-file submission/.env -f submission/compose.yaml exec -T miniapp python tools/data-api/validate_data_api.py DATA-API.yaml --schema tools/data-api/DATA-API.schema.json --openapi openapi.yaml
npm ci --ignore-scripts
npm test
```

Python/PG на отдельной локальной БД, после `up`:

```sh
python tools/submission/check_components.py
```

При изменённом локальном пароле задать соответствующий `PLANNER_TEST_DSN` через окружение: `postgresql://support_router:ЛОКАЛЬНЫЙ_ПАРОЛЬ@postgres/support_router`. DSN проверяется: разрешён только сервис `postgres` с локальной базой `support_router`. Никогда не использовать production DSN.

Runner собирает оба варианта образа, запускает тесты miniapp и четыре теста отличающегося MAX-меню на соответствующем варианте bot. Он создаёт отдельную внутреннюю Docker-сеть без выхода в интернет; подключает к ней только одноразовый PostgreSQL и тестовые контейнеры. Провайдерные ключи в тесты не передаются, MAX-токен инертный. Каждая PostgreSQL-проверка создаёт и удаляет свою временную схему. В конце тестовая сеть удаляется; volume локального Compose остаётся для повторного запуска.

`submission/rollback-source` содержит исторический совместимый код выпуска `0846580` из ранее сохранённого архива; SHA-256 архива и файлов — в `PROVENANCE.json`. Это read-only fixture для проверки сохранения остановки бота, удаления данных одного синтетического владельца и возврата к новой версии. Она не является инструкцией отката текущего production. Исторические runtime-файлы не изменены; добавлена только пустая синтетическая директория `project/logs` для конструктора прежнего Runner. Контрольные суммы fixture проверяются до тестов; отсутствие fixture прерывает runner. Он не пропускает проверку совместимости молча.

Полный состав тестов: `project/llm/tests`, `project/admin/tests`, `project/miniapp/tests`, `tools/submission/test_backup_retention.py`, `tools/submission/test_data_api_runner.py`; отдельные bot-only случаи перечислены в runner. Локальные тесты LLM/транспорта контролируются заглушками и не являются live MAX/provider. Итоговые количества и отдельная живая проверка — в VERIFICATION.md.

В комплект возвращён `docs/ai-quality-repair/card-inputs-02.json`; проверки каталога и selector-заглушки соответствуют текущим данным и схеме ответа. Очистка тестовой схемы учитывает статусы жилья/работы и их последовательности. Seed создаёт хранилища сеансов и избранного перед миграциями планировщика; `pypdf==6.11.0` включён в проверочные зависимости. В тесте формы повреждённого provider-ответа deadline равен 10 с, чтобы отдельно проверять нормализацию `invalid_response`; строгий тест deadline 0,01 с и runtime-таймеры сохранены. Обоснование и контролируемые replay — `VERIFICATION.md` и evidence.

Дополнительно 25 чистых проверок бюджета и предиката отказа выполняются без обращений к поставщику: `docker compose --env-file submission/.env -f submission/compose.yaml exec -T miniapp python -m pytest -q tools/submission/test_acceptance_live_budget.py tools/submission/test_acceptance_live_assessor.py`. Их импорт не запускает живой прогон. Исходные ответы, отдельная офлайн-переоценка и неизменённый журнал расходов находятся в `evidence/AI-LIVE/` закрытого комплекта.

Из корня репозитория: `python tools/submission/verify_acceptance.py .` проверяет файлы манифеста.

## API и доступы

`openapi.yaml` выгружен из фактического приложения; `DATA-API.yaml` описывает проверки, роли, параметры, коды и поля. Health/info и каталог помощи открыты. Личные API требуют bearer из `POST /api/session` с подписанными `init_data` MAX. Bearer ограничен по времени и отзывается при удалении аккаунта. Токен бота не является bearer; общего логина/пароля нет.

Публичный режим `tools/submission/check_api.py` выполняет только операции роли public и пропускает пользовательские записи. Полный `--full` допускается только на одноразовом loopback-стенде: синтетический bearer передаётся через `DATA_API_SESSION`, рабочий MAX-токен и реальный аккаунт не нужны. Runner проверяет избранное и полный plan-cycle: подтверждение плана, точный повтор, чтение, перенос даты, выполнение, повторное чтение, удаление созданных дела/цели и итоговые 404. После прогона удаляется только синтетический аккаунт. Адрес внешнего сервиса отклоняется до первого запроса. Подробные команды и правила cleanup — `docs/data-api/README.md`.

## Ограничения и безопасность

HMAC-SHA256 подпись и срок запуска проверяются на backend; owner берётся из подписи. Изоляция владельцев, конфликты версий, повтор действий, удаление и отзыв сеансов покрываются тестами. Личные данные не принимают чужой owner из тела запроса. Секреты не передаются frontend. Данные в резервных копиях удаляются по сроку хранения, не мгновенно.

Статусы жилья/работы вводит пользователь. Форма https://www.gosuslugi.ru/676953/1 подписана «Новосибирская область» и не выдана за универсальную. Право, суммы, наличие услуг и объявления уточняются в своём регионе/организации. Каталоги требуют редакционного обновления. Пилот и социальный эффект пока не подтверждены. Резерв на одном VPS не защищает от потери сервера.

Native MAX/iOS/Android, доставка уведомлений и live-провайдер проверяются отдельно от локальных браузеров/PG. Фиксированные requirements не гарантируют побайтовое повторение будущих базовых Docker-образов.

## Остановка и повторный запуск

```sh
docker compose --env-file submission/.env -f submission/compose.yaml down
docker compose --env-file submission/.env -f submission/compose.yaml up -d
```

Без `-v` volume сохраняется. Профиль bot выключен по умолчанию. Не запускать второй poller с токеном действующего бота; для своего отдельного развёртывания использовать собственный токен, HTTPS, БД и production-конфигурацию.


## Дополнительный синтетический HTTP/браузерный стенд

После `up` можно выполнить `python tools/submission/check_acceptance_local.py`.
Он запускает два локальных экземпляра на 18976/18977 с инертным токеном,
проверяет подписи синтетических владельцев, план/дату/выполнение, избранное,
статусы, изоляцию владельцев, рестарт и отзыв сеансов. Платные сервисы и MAX
не вызываются; тестовые записи удаляются. Результат — `evidence/LOCAL-HTTP.json`.

После `npm ci --ignore-scripts` и `npx playwright install chromium webkit`:
`node tools/submission/acceptance_browser.cjs` проверяет восемь комбинаций
Chromium/WebKit, 320/393px, светлой/тёмной темы. Скриншоты и BROWSER.json —
в browser-evidence. Это тестовый мост к локальному серверу с синтетическим
токеном, а не настоящий клиент MAX. Production-проверки так не запускать.

По завершении остановить только два созданных стендом контейнера:
`docker rm -f tochka-acceptance-v2-audit-signed-20261026 tochka-acceptance-v2-audit-signed-20261026-second`.
Их данные хранятся только в отдельном volume локальной приёмки.
