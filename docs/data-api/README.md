# Проверки API приёмки

`DATA-API.yaml` описывает публичные проверки и роль `user`. `openapi.yaml` фиксирует методы, тела запросов и форматы ответов. Контракт соответствует схеме DATA-API 1.0, копия схемы и валидатор находятся в `tools/data-api/`.

## Публичный режим

```sh
python tools/submission/check_api.py --output public-api-results.json
```

Этот режим проверяет публичный HTTPS из контракта и пропускает все операции роли `user`, в том числе создание/изменение/удаление планов и cleanup. Единственный публичный POST — отказ в создании сеанса по пустой неподписанной строке. Он не даёт доступ и не создаёт пользовательский сеанс. Публичный режим не проверяет плановые записи, внешние поиски и новую генерацию ИИ.

## Полный локальный режим

Полный цикл разрешён только для одноразового локального стенда на loopback. Runner отклоняет внешний адрес до первого запроса. Создать локальные подписанные серверы можно штатным `tools/submission/check_acceptance_local.py`, который использует инертный тестовый MAX-токен. Для отдельного синтетического владельца получить bearer через `/api/session` на том же стенде. Production-данные, рабочий MAX-токен и настоящий пользовательский сеанс для этого не нужны.

Передать синтетический bearer через переменную окружения `DATA_API_SESSION`, затем выполнить из корня исходников:

```sh
python tools/submission/check_api.py --base-url http://127.0.0.1:18976 --full --output local-api-results.json
```

После прогона удалить именно синтетический аккаунт через `DELETE /api/account`, чтобы отозвать сеанс и удалить его служебные квитанции повторных запросов. Нельзя применять эту очистку к реальному аккаунту MAX.

`runId`, `goalId`, `taskId` — новые UUID на каждый полный прогон. Они создаются runner до запросов. Это начальные переменные тестового окружения, а не существующие записи. Поля `${testTaskVersion}` и `${testGoalVersion}` берутся через `extract` из ответов и подставляются числами. Шаблон, равный переменной целиком, сохраняет JSON-тип, а встроенная переменная в строке остаётся строкой.

Цикл `plan-cycle-*` подтверждает план с одной целью и одним делом, повторяет тот же запрос с прежним Idempotency-Key, читает дело, меняет дату, отмечает выполнение, перечитывает результат, затем удаляет созданное дело и опустевшую цель. Последние чтения ожидают 404. Все записи имеют уникальные UUID. Уведомления не создаются, ИИ и поставщики вакансий/аренды не вызываются.

Cleanup выполняется и после ошибки. Он удаляет только полученные из этого прогона ID, использует последние полученные версии и те же ключи удаления. Если ошибка не позволила получить ID/версию, шаг помечается пропущенным. Ошибка cleanup делает прогон неуспешным. После сетевого обрыва на записи может потребоваться ручная проверка конкретного синтетического владельца и окончательное удаление его локального аккаунта.

## Структурная проверка

```sh
python tools/data-api/validate_data_api.py DATA-API.yaml --schema tools/data-api/DATA-API.schema.json --openapi openapi.yaml
python -m unittest tools.submission.test_data_api_runner
```

Валидатор может предупреждать, что начальные UUID не получены через `extract`: их специально создаёт runner. Это не секреты и не ссылка на чужие пользовательские данные. Структурная валидация сама по себе не доказывает успешное выполнение HTTP-сценария.
